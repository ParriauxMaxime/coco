Runs the app dev servers of the worktrees your agents work in: one server per worktree, on a port that stays the same across restarts, so agents ask for a server instead of each starting their own.

The plugin reads the `devServers` key of a JSON config file. Settings → Plugins → coco dev servers sets that file (`~/cocopilot/coco.config.json` by default) and the API port, and shows whether the config loaded and which projects it lists. Each project says how to recognize its repository, which command starts its dev server, and which port range to use.

Ports come from the project's range, one step at a time. A worktree keeps its port until its directory is removed. Excluded ports and ports another process listens on are skipped, and every port a server reserves, such as a debugger port at a fixed offset, stays apart from the ports of other worktrees. State lives in `~/.cocopilot/dev-servers` by default.

Each server runs in its own process group, detached from Paseo, with its output appended to `logs/<server>/run.log` in the state directory, so it keeps running when the plugin reloads or the daemon restarts. On its next start the plugin finds its servers again from the recorded pid, start time and directory; a pid that now belongs to another process is never touched. The plugin follows each server through building, ready and crashed from its log and an HTTP check, and a stop ends the whole process group, then any leftover process still running in the directories the project lists.

A project can name a settings file its dev server reads (`settings.file`, relative to the worktree). Before each start the plugin writes that file as your own content plus an overlay: the templated `settings.overlay` (for example `"logDir": "{logDir}"`), then whatever the `settingsOverlay(ctx)` export of the project's `provider` module returns. Your own content is kept in `base/` in the state directory, and a stop writes it back (or removes the file if you had none). An edit you make to the generated file is noticed, copied aside, and kept in your own content. The file must be plain JSON.

A JSON API on `127.0.0.1` (port 8779 by default) starts, lists, stops and tails the servers: `POST /api/servers/start` with `{ "cwd": "<worktree path>" }`, `GET /api/servers`, `GET /api/servers/<id>`, `POST /api/servers/<id>/stop`, `GET /api/servers/<id>/logs?lines=100&grep=error`. POST bodies must be `application/json`, and requests from a non-loopback Host or Origin are refused, so web pages cannot drive it. Errors come back as `{ "error": { "code", "message" } }`.

Every agent Paseo creates in a configured project (any provider; `injectMcp: "all"` for every directory, `"off"` for none) gets a `dev-servers` MCP server on the same port at `/mcp`, with its tools loaded up front and preapproved: `dev_server_start`, `dev_server_status`, `dev_server_stop` and `dev_server_logs`. Each agent gets its own key, so the plugin knows its directory and which servers it holds. Agents created before the plugin was installed have no tools and can use the JSON API.

A server stays up while someone holds it. Starting it takes a hold; stopping it, archiving the agent, or not using it for `leaseTtlMinutes` (240 by default) lets go. A server nobody holds shows as idle and stops after `idleStopMinutes` (30 by default) unless it is pinned or someone starts it again. These deadlines survive plugin reloads. Agent tools never force a stop: a server another agent holds keeps running.

Worktrees of a stack share one server. A start from a lower worktree is served by the top of its stack: another worktree under `worktreeRoots` (or the project's `mainCheckout`) whose commit contains the caller's, with no worktree built on top of it. A running server whose worktree is clean and contains the caller's commit is reused first, so nothing builds. The caller runs its own server when it has uncommitted changes, when its commit is already on `origin`'s default branch, when nothing builds on it, or when it asks for a dedicated server, services or a dedicated database. A top with uncommitted changes still serves, and the reply names its changed files. When two stacks build on the caller's commit, the plugin asks coco (`coco.url`, `null` to turn it off) which work the branch belongs to and takes that work's latest row; when coco cannot tell, the caller runs its own server and the reply lists the tops under `placement.ambiguous`, to pick one with `serveFrom` on the next start. `placement.because` always says why.
