Runs the app dev servers of the worktrees your agents work in: one server per worktree, on a port that stays the same across restarts, so agents ask for a server instead of each starting their own.

The plugin reads the `devServers` key of a JSON config file. Settings → Plugins → coco dev servers sets that file (`~/cocopilot/coco.config.json` by default) and the API port, and shows whether the config loaded and which projects it lists. Each project says how to recognize its repository, which command starts its dev server, and which port range to use.

Ports come from the project's range, one step at a time. A worktree keeps its port until its directory is removed. Excluded ports and ports another process listens on are skipped, and every port a server reserves, such as a debugger port at a fixed offset, stays apart from the ports of other worktrees. State lives in `~/.cocopilot/dev-servers` by default.

Each server runs in its own process group, detached from Paseo, with its output appended to `logs/<server>/run.log` in the state directory, so it keeps running when the plugin reloads or the daemon restarts. On its next start the plugin finds its servers again from the recorded pid, start time and directory; a pid that now belongs to another process is never touched. The plugin follows each server through building, ready and crashed from its log and an HTTP check, and a stop ends the whole process group, then any leftover process still running in the directories the project lists.

A project can name a settings file its dev server reads (`settings.file`, relative to the worktree). Before each start the plugin writes that file as your own content plus an overlay: the templated `settings.overlay` (for example `"logDir": "{logDir}"`), then whatever the `settingsOverlay(ctx)` export of the project's `provider` module returns. Your own content is kept in `base/` in the state directory, and a stop writes it back (or removes the file if you had none). An edit you make to the generated file is noticed, copied aside, and kept in your own content. The file must be plain JSON.

A JSON API on `127.0.0.1` (port 8779 by default) starts, lists, stops and tails the servers: `POST /api/servers/start` with `{ "cwd": "<worktree path>" }`, `GET /api/servers`, `GET /api/servers/<id>`, `POST /api/servers/<id>/stop`, `GET /api/servers/<id>/logs?lines=100&grep=error`, `POST /api/servers/<id>/pin` with `{ "pinned": false }` to unpin, `POST /api/servers/<id>/login` with `{ "user", "path" }` (both optional), and `GET /api/placement?cwd=<path>` to see which server a start would use without starting anything. POST bodies must be `application/json`, and requests from a non-loopback Host or Origin are refused, so web pages cannot drive it. Errors come back as `{ "error": { "code", "message" } }`.

Every agent Paseo creates in a configured project (any provider; `injectMcp: "all"` for every directory, `"off"` for none) gets a `dev-servers` MCP server on the same port at `/mcp`, with its tools loaded up front and preapproved: `dev_server_start`, `dev_server_status`, `dev_server_stop`, `dev_server_pin`, `dev_server_logs` and `dev_server_login`. Each agent gets its own key, so the plugin knows its directory and which servers it holds. Agents created before the plugin was installed have no tools and can use the JSON API.

A server stays up while someone holds it. Starting it takes a hold; stopping it, archiving the agent, or not using it for `leaseTtlMinutes` (240 by default) lets go. A server nobody holds shows as idle and stops after `idleStopMinutes` (30 by default) unless it is pinned or someone starts it again. These deadlines survive plugin reloads. Agent tools never force a stop: a server another agent holds keeps running. An agent can pin the server it uses and undo its own pin, never someone else's.

At most `cap` servers run at once (3 by default), counting servers that build, serve, sit idle or crashed with their process still up, prebuilds while they build, and servers started by hand. A start at the cap first cancels a prebuild, else stops the least recently used server that is neither pinned nor started by hand, and lists it under `evicted`. When every slot is pinned or started by hand, the start fails with `capacity_full` and the list. An agent whose server was stopped under it, to make room or by a forced stop, finds a `lost` notice in its next tool reply.

A project with an `adopt` block takes in dev servers started by hand: every 30 seconds and before each start, the plugin looks for listening processes whose directory is exactly `<worktree>/<appDir>` of one of the project's worktrees (and matches `adopt.cwdPattern` when set) and whose port answers `adopt.probe`. Such a server shows as `external`: it counts toward the cap, serves its own worktree and, when its worktree is clean, the worktrees below it in a stack, and the plugin never stops it, evicts it nor reads its output. Asking it for services or a dedicated database is refused, and asking for services while one runs warns that they may run twice. It disappears from the list once its process stops listening.

Worktrees of a stack share one server. A start from a lower worktree is served by the top of its stack: another worktree under `worktreeRoots` (or the project's `mainCheckout`) whose commit contains the caller's, with no worktree built on top of it. A running server whose worktree is clean and contains the caller's commit is reused first, so nothing builds. The caller runs its own server when it has uncommitted changes, when its commit is already on `origin`'s default branch, when nothing builds on it, or when it asks for a dedicated server, services or a dedicated database. A top with uncommitted changes still serves, and the reply names its changed files. When two stacks build on the caller's commit, the plugin asks coco (`coco.url`, `null` to turn it off) which work the branch belongs to and takes that work's latest row; when coco cannot tell, the caller runs its own server and the reply lists the tops under `placement.ambiguous`, to pick one with `serveFrom` on the next start. `placement.because` always says why. When the caller's worktree changes so that the server it holds would no longer serve it, for example after uncommitted changes or a restack, `dev_server_status` marks that server `stale` and says to start again.

A project's `warm` block fills a fresh worktree from the same paths in its `mainCheckout` before its server first starts: `symlink` links a directory such as `node_modules`, `clone` copies a build cache copy-on-write (`cp -c` on APFS, `cp --reflink=auto` on Linux, a plain copy elsewhere), and `copyIfMissing` copies a file. A path that already exists is never touched, and a cache is not cloned while the main checkout's own server builds.

With `warm.prebuild` on, every worktree Paseo creates for the project, except the main checkout, is prebuilt: warmed, then its server is built with every opt-in off, shown as `prewarming`, and stopped once ready, which leaves a hot build cache for the first real start. Prebuilds wait in one queue and run one at a time, oldest first. A prebuild counts toward the cap only while it builds and never stops another server: at the cap it waits and tries again later. A start at the cap cancels a prebuild before any other server; the cancelled prebuild goes back to the end of the queue, and is dropped after three cancellations. A start for a worktree whose prebuild is queued takes the job out, and a start during its build takes it over: the build goes on, and the server stays up as a normal one. The queue survives plugin reloads.

Archiving a Paseo workspace drops its queued prebuild and the holds of the agents created in it. Its server stops unless it is pinned, started by hand, or held from another worktree; once stopped, its port is released and its record and kept settings are forgotten.

A project's `provider` module can export `login(ctx)` to open a ready server logged in. It gets the server's id, worktree, `appDir`, port, url and log folder, plus the `user` and `path` the caller asked for, and returns `{ url, seed?, expiresAt?, user? }`, where `seed` is `{ storage: "localStorage", origin, entries }` on the same origin as `url`. The reply hands the agent the seed as one browser function to run on that origin (`apply.function`, or `apply.script` as statements for an init script), then the page to open. A server that is not ready yet is refused with `not_ready`, a project without `login` with `login_unavailable`, and a provider that throws, returns another shape or takes longer than `login.timeoutSeconds` (60 by default) with `login_failed`.

In Paseo, the sidebar footer shows how many slots are taken and how many servers build or crashed, for example `Dev servers 2/3 · 1 building`, and opens the Dev servers screen: one card per server with its worktree, branch, port, url, state, who holds it, its pin, opt-ins and their reason, when it stops if nobody uses it, and the agents that lost it. Each card opens the server, opens it logged in (open the server, then paste one snippet in its developer console that stores the session and goes to the page), shows its log tail, pins or unpins it, and stops it after a confirmation: a plain stop when only you hold it, a forced stop that names who loses it otherwise. The Dev server panel of a workspace (also in ⌘K) says which server serves its worktree and why, lets you start it, start a dedicated one or pick a stack top when the plugin cannot tell, and shows the same card with its log open. A server you start from Paseo is held by you until you stop it. Each agent that holds a server gets a pill in its composer with the state and port, which opens the panel, and a row in its timeline when its build turns ready or when its server is stopped under it. The screens poll the plugin every few seconds; reading the logs there does not count as using the server.
